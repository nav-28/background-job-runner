# Job Runner

Submit background work, watch it run, collect the result.

Work is submitted to a named **lane**, queued, and executed by a worker pool. Every task gets a
short handle (`scrape-1`) and a stable uuid. The dashboard streams state changes live.

```
POST /tasks {lane}  →  queued  →  running  →  ready  →  collected
                                     ↓
                                   failed  →  retry
```

## Stack

**Backend** — Node 24, Fastify 5, Postgres 18. TypeScript throughout, run natively by Node with no
build step. TypeBox for schemas, `postgres.js` for queries, dbmate for migrations, `node:test` for
tests.

**Frontend** — Next.js 15 (App Router), React 19, MUI 7, TanStack Query, Zustand. The API client is
generated by Orval from the backend's OpenAPI document.

**Both** — pnpm workspace, Biome for lint and formatting, Docker Compose for the whole stack.

## Layout

```
backend/src/engine/     the queue, worker pool and task lifecycle — no Fastify
backend/src/modules/    HTTP: auth, api keys, tasks
backend/src/workers/    the lanes this deployment can run
frontend/src/           Next.js dashboard
```

The engine is a library that happens to live here. It never imports Fastify; the HTTP layer is one
caller and the tests are another. Adding a lane is one entry in the array in
`backend/src/plugins/engine.ts`.

## Postgres is the queue

The task table _is_ the queue, claimed with
`FOR UPDATE SKIP LOCKED`.

A queue library like BullMQ would have brought its own storage, and every question worth asking here — is this
durable, who owns this handle, what happened to task 7 — is a question about task state. Splitting
that across two stores would have meant reconciling them. One database means a claim and its state
change are the same transaction.

## Handles are recycled

`scrape-1` is the _lowest free number in that lane, for that user_. When a task is collected or
cancelled, the number returns to the pool and a later task can take it.

That makes handles friendly to type and unsafe to store. A partial unique index enforces that only
one live task holds a number:

```sql
CREATE UNIQUE INDEX tasks_active_handle_uniq ON tasks ("userId", lane, "handleNum")
  WHERE status IN ('queued','running','failed') OR (status = 'ready' AND NOT collected);
```

The database, not the application, is what makes double-allocation impossible. Concurrent submits
serialise on a per-lane advisory lock, and the index is the backstop if that is ever bypassed.

The UI addresses tasks by uuid for exactly this reason, and reads history by id — the handle form
answers for whoever holds the number _now_.

## Surviving a restart

Work in flight when a process dies is not lost.

- **Write before act.** A task is marked `running` and committed before the worker is invoked, so a
  crash mid-job leaves evidence.
- **Leases.** A claim carries an expiry, refreshed by a heartbeat while the job runs. A lease that
  stops being refreshed is reclaimed.
- **Boot sweep.** On start, tasks left `running` by a previous life are requeued.
- **Graceful drain.** On shutdown in-flight jobs finish first, in `preClose` — `onClose` hooks run
  LIFO and the database connection would close underneath them.

This is **at-least-once**: a job can run twice if a process dies after the work completes but before
the result commits. Exactly-once would need the workers to be transactional with the queue, which
they are not. Workers should be idempotent.

## Live updates

`GET /events` is a Server-Sent Events stream, one connection per session, opened by the app layout
so navigation doesn't reconnect.

Events are treated as a **hint to refetch**, never as data to patch into the cache. The database
stays the only thing that decides what a task's status is, which means a dropped or truncated event
costs a redundant fetch rather than a wrong screen. Reconnects replay via `Last-Event-ID`.

## The frontend client is generated

Route schemas are TypeBox, which validates requests, serialises responses, _and_ becomes the OpenAPI
document. Orval turns that into typed TanStack Query hooks.

The client cannot disagree with the API, because nobody writes it. `pnpm generate:api:live`
regenerates from a running backend.

One hand-written exception: the SSE payload type. Streams have no response schema, so they never
reach the OpenAPI document.

## Scope

Built to be honest about what it is rather than to look finished:

- **Workers are simulated.** `scrape` and `report` sleep and return a payload. The engine has no
  opinion about what a worker does.
- **Single process.** Concurrency is a worker pool inside one Node process. Scaling to several
  replicas would work — claims are already race-safe — but `ENGINE_BOOT_SWEEP` must be off first, or
  a booting process would requeue its peers' live work.
- **In-process workers.** A CPU-bound worker would block the event loop. Real ones would move to
  worker threads or a separate process; the engine's interface would not change.
- **`GET /tasks` caps at 100 rows** and returns no total count, so the UI pages by growing its
  request rather than pretending to know how many pages exist.
- **Event replay caps at 500.** Fine under the refetch-hint rule above.

## Tests

160 backend tests: the engine against a real Postgres, the API through HTTP, plus durability tests
that kill a child process mid-job and assert the work is recovered.

```bash
cd backend && pnpm test              # unit
cd backend && pnpm test:integration  # needs Postgres
```

Integration tests truncate the database. `pnpm db:seed:reset` restores the demo data.

## Github Codespaces

This repo is setup up to work inside github codespaces. To test out the live server, make sure that 
the backend api's visibility is set to `Public` so that the frontend can make API requests. 

If project doesn't run on its own, open a terminal and run `./.devcontainer/post-create.sh` to create
the postgres container and seed the db. Then finally run `pnpm dev` to start the dev server.
